# Human Approval and Governance

## Principle

Humans supervise. Machines work.

## State-changing actions

Any action that changes, deletes, publishes, sends, edits, creates, confirms, cancels, pays, communicates externally, or otherwise affects real organizational/system state must pass the applicable approval policy.

## Approval object

A reviewable approval should contain:

- category/type
- approval subject
- request owner
- approver(s)
- minimum approvals required
- requested fields defined by the category
- internal action and target record(s), when the approval is generated by another module
- requested change
- reason
- evidence/context
- AI recommendation (if any)
- confidence/uncertainty where meaningful
- policy requiring approval
- requester/agent
- timestamp
- resulting audit record

## UX

Requester-facing approval screens must be Approval Type first. The user chooses
an approval type, fills the request fields, and submits to the configured
approvers. Requesters must not be asked to enter technical target model names,
record IDs, or backend method names.

Approval Type configuration should explain what the type is for, who can
approve, whether the requester manager is part of the approval chain, whether
sequence matters, and the minimum number of approvals required. The default
minimum approval is 1.

Primary actions:
- Approve
- Refuse
- Edit/Adjust
- Ask AI / Explain
- View evidence

The approval UI should make the decision understandable without forcing the user through the entire ERP record unless needed.

## Naming and presentation

Use clear product names, descriptions, and icons for approval-related modules.
For the main project approval experience, prefer the name `Approval Center`
unless a narrower module scope requires a more specific name. Descriptions must
explain the business outcome in one sentence, not only list technical features.
Icons should be intentionally selected and consistent with Odoo-style module
icons; the Odoo Approvals icon URL provided as a reference is
`https://download.odoocdn.com/icons/approvals/static/description/icon.svg`.

## Automation activation

A learned automation is not active merely because AI detected it.

Activation requires explicit user confirmation of the automation definition and its policy.

## Audit

Every approval and execution must be traceable.

## Odoo execution rule

When an approved request maps to existing Odoo behavior, execute it through the
module's public action method instead of writing final states directly. The
approval layer must enforce policy before calling the action and record the
audit result after the action completes or fails.
