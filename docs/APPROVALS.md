# Human Approval and Governance

## Principle

Humans supervise. Machines work.

## State-changing actions

Any action that changes, deletes, publishes, sends, edits, creates, confirms, cancels, pays, communicates externally, or otherwise affects real organizational/system state must pass the applicable approval policy.

## Approval object

A reviewable approval should contain:

- category/type
- approval subject
- request owner
- approver(s)
- minimum approvals required
- requested fields defined by the category
- internal action and target record(s), when the approval is generated by another module
- requested change
- reason
- evidence/context
- AI recommendation (if any)
- confidence/uncertainty where meaningful
- policy requiring approval
- requester/agent
- timestamp
- resulting audit record

## UX

Requester-facing approval screens must be Approval Type first. The user chooses
an approval type, fills the request fields, and submits to the configured
approvers. Requesters must not be asked to enter technical target model names,
record IDs, or backend method names.

Approval Type configuration should explain what the type is for, who can
approve, whether the requester manager is part of the approval chain, whether
sequence matters, and the minimum number of approvals required. The default
minimum approval is 1.

Primary actions:
- Approve
- Refuse
- Edit/Adjust
- Ask AI / Explain
- View evidence

The approval UI should make the decision understandable without forcing the user through the entire ERP record unless needed.

## Naming and presentation

Use clear product names, descriptions, and icons for approval-related modules.
For the main project approval experience, prefer the name `Approval Center`
unless a narrower module scope requires a more specific name. Descriptions must
explain the business outcome in one sentence, not only list technical features.
Icons should be intentionally selected and consistent with Odoo-style module
icons; the Odoo Approvals icon URL provided as a reference is
`https://download.odoocdn.com/icons/approvals/static/description/icon.svg`.

## Automation activation

A learned automation is not active merely because AI detected it.

Activation requires explicit user confirmation of the automation definition and its policy.

## Audit

Every approval and execution must be traceable.

## Odoo execution rule

When an approved request maps to existing Odoo behavior, execute it through the
module's public action method instead of writing final states directly. The
approval layer must enforce policy before calling the action and record the
audit result after the action completes or fails.

## Telegram setup diagnostic

The manager's explicit **Send test message** confirmation authorizes one fixed
setup diagnostic (`Telegram connection test successful.`) to the displayed first
personal Telegram test-user ID entered on that scoped connection. The same
confirmation authorizes the listed test users and displayed retention policy,
and enables receiving before claiming the diagnostic.
This narrow setup policy permits no arbitrary text, recipient, group, business
reply, dispatch activation or scheduler change. The tester must have started the
bot. Blocked identities remain blocked. Normal replies retain recipient consent
and Approval Center review.

The execution boundary commits an actor-audited claim before network I/O. A
pending, successful or uncertain claim cannot be repeated. Only a confirmed
not-sent outcome permits another explicit attempt. Provider errors are sanitized;
no automatic retry occurs. Finish setup requires a confirmed successful test and
selects the verified bot as runtime sender; it does not enable business dispatch.

## WhatsApp setup diagnostic

A scoped manager's explicit **Send test message** confirmation authorizes one
fixed message (`WhatsApp connection test successful.`) to the displayed tester
phone number and attests that the tester agreed to receive it. No arbitrary text,
group, template, business reply, automation or dispatch activation is authorized.
The tester must have sent a verified private message to this exact endpoint within
the last 24 hours under the current intake policy. Blocked testers stay blocked.

An actor-audited attempt is committed before the POST. Pending, accepted and
uncertain attempts cannot repeat. Only a confirmed provider rejection permits
another explicit attempt. No automatic POST retry is allowed. Provider acceptance
does not prove delivery: the manager must confirm that the tester received it.
Finish setup checks the current credential/callback/tester fingerprint and selects
the sender through its existing public activation action. Business dispatch and
the scheduler remain disabled. Normal business replies still need their own
consent and Approval Center policy; this diagnostic grants no permission for them.
Withdrawing receipt confirmation removes the final milestone and selected sender.
Changing connection configuration similarly clears completion. An unresolved
attempt cannot be discarded to permit another send. A confirmed receipt permits
a new configuration to start its own explicitly confirmed diagnostic.

## Slack setup diagnostic

A scoped manager's explicit **Send test message** confirmation permits one fixed
`Slack connection test successful.` message to the displayed tester's verified
private Slack conversation and attests agreement. A retained incoming message
from that tester is required. Blocked identities remain blocked. An actor-audited
claim commits before I/O; pending, accepted and uncertain results cannot repeat.
Only a definitive not-sent rejection permits a fresh explicit attempt. Receipt
confirmation is required to finish; withdrawing it clears completion and selected
sender. Setup does not enable business dispatch. Normal private text replies use
the existing recipient consent, Approval Center and dispatch governance.

## Microsoft Teams setup diagnostic and approved replies

A scoped manager's explicit **Send test message** confirmation permits one fixed
`Teams connection test successful.` message to the selected, recent, authenticated
personal chat and attests agreement. The tester is shown by name in the chat
selector. Blocked identities remain blocked. An actor-audited claim commits before
I/O; pending/accepted/uncertain attempts cannot repeat. A definite not-sent result
permits a new explicit attempt. Receipt confirmation is required to finish;
withdrawing it removes completion and deactivates the sender.

For Slack and Teams, **Enable approved replies** authorizes new dispatch claims
only on the current, tested connection with an active company approval policy.
It does not grant recipient consent or approve any message. Existing consent,
Approval Center, sender generation, immutable payload, outbox claim and uncertain
outcome controls apply. **Pause replies** stops new claims. The existing global
dispatch scheduler remains separately administered; neither setup nor the channel
reply button activates it.
